## 2. `bin-01` : la promesse fausse est réparée (prouvé hors image)

**Constat d'origine** : la room promettait un shell root. Le binaire ne
contenait aucun chemin vers un shell (`strings` : zéro `/bin/sh`, `objdump` :
aucun `system`, aucun `execve`). Aucun élève ne pouvait obtenir le drapeau par
l'exploitation.

**Réparation** : la lecture se fait par `read()` dans un tampon de 64 octets,
et le programme contient désormais une fonction `carnet_root` — jamais appelée
par le cours normal — qui remet les identités à zéro puis ouvre un shell.

**Preuve** (reproductible en une commande) :

```
$ cd labs/bin-01/src && make
$ cd ../../.. && python3 tools/recette-apprenants/exploit-bin01.py \
      labs/bin-01/src/vulnerable --commande "id; echo SECA-SHELL-OK"
carnet_root      : 0x0000000000401196
bourrage retenu  : 88 octets
...
> uid=1001(user) gid=1001(user) groups=1001(user),27(sudo),100(users)
SECA-SHELL-OK
IDENTITE DU SHELL : pas root (normal hors image : le binaire doit etre setuid root)
```

**Ce qui reste non prouvé** : le shell **root** et la lecture de
`/root/flag.txt` (`FLAG=SECURA{buffer_overflow}`). Cela exige l'image Docker,
donc la mesure GitHub (§4). Hors image, le binaire n'est pas setuid : le shell
s'ouvre avec l'identité de l'utilisateur.

Le contrôle machine correspondant a été remplacé : il ne se contente plus de
lire le drapeau en root (ce qui ne prouvait rien), il exécute
`tools/recette-apprenants/exploit-bin01.py` **dans le conteneur** et exige le
drapeau en sortie.

## 2 bis. Le run réel du soir : la promesse restait fausse, et le banc le prouve

Run `42035854451` (commit `248cc29`), déclenché à 13:27, **18 minutes**,
vrai Docker. Résultat : **rouge**, avec une annotation lisible cette fois :

```
ECHEC : controles des machines (voir /tmp/machines.txt)
```

Le registre d'échecs a fait son travail : il a nommé la mesure fautive au lieu
de laisser un `exit 1` anonyme. Restait à comprendre.

### Ce que le test a révélé (et qui change le diagnostic)

Mon premier exploit tournait **hors conteneur**, sans setuid : j'en avais
conclu « le shell s'ouvre, il n'est simplement pas root ». C'était le mauvais
diagnostic. Les deux conditions réellement nécessaires n'ont jamais été
réunies :

| Condition | Hors bac à sable | Dans l'image (`docker run`) |
|---|---|---|
| binaire `setuid root` (`chmod 4755`) | non | **oui** |
| `--security-opt no-new-privileges` | non | **oui** — et c'est ce qui tue le scénario |

`no-new-privileges` demande au noyau d'ignorer le bit setuid. Le shell
s'ouvrait donc, mais en simple utilisateur : **le drapeau restait
illisible**. La room promettait un shell root qui ne pouvait pas exister dans
les conditions où la plateforme lance les machines.

### Preuve mesurée, ici, sans Docker (sudo disponible localement)

```
$ chown root:root /tmp/suid/vulnerable && chmod 4755 /tmp/suid/vulnerable
$ python3 tools/recette-apprenants/exploit-bin01.py /tmp/suid/vulnerable \
      --commande "id; cat /root/flag_test.txt"
bourrage retenu  : 88 octets
> uid=0(root) gid=1001(user) groups=1001(user),27(sudo),100(users)
FLAG=SECURA{preuve_locale}
IDENTITE DU SHELL : root
```

Et la démonstration du défaut, sur **le même binaire** :

```
$ setpriv --no-new-privs python3 tools/recette-apprenants/exploit-bin01.py \
      /tmp/suid/vulnerable
bourrage  88     : echec (code 1)
AUCUN SHELL : le scenario ne peut pas aboutir
```

Même binaire, même exploit, même offset : la seule différence est
`no-new-privileges`. C'est la cause racine, démontrée, pas supposée.

### Les corrections

1. **Le manifeste peut demander le setuid** (`allow_setuid`), et il reste
   fermé par défaut. `no-new-privileges` est toujours appliqué — sauf pour la
   room qui **enseigne** précisément le setuid. Toutes les autres limites
   restent : `--cap-drop ALL`, réseau fermé, mémoire, pids, `/tmp` nosuid.
2. **Le test machine ne pouvait pas valider ce qu'il mesurait** : il lançait
   `bin-01` avec `no-new-privileges`, donc dans des conditions où le scénario
   est impossible. Il applique maintenant le manifeste.
3. **Deuxième fuite trouvée en chemin** : le drapeau `SECURA{buffer_overflow}`
   était écrit en clair dans la sortie d'un terminal simulé de la room
   (`cat /root/flag.txt` → drapeau, sans aucune exploitation). Il répond
   désormais `Permission denied` tant qu'aucun shell root n'est obtenu — et un
   contrôle machine vérifie qu'il ne traîne nulle part dans `/home/ctf`.

Ce troisième point est le plus instructif : même réparé, un lab peut rester
une coquille vide si le drapeau se trouve ailleurs que derrière l'effort
demandé.

## 4. Ce que je ne peux pas faire d'ici, et qui ne dépend que d'un clic

Le bac à sable n'a ni Docker ni droit de lancer un workflow (l'API répond
`HTTP 403 : Resource not accessible by integration`). La mesure sur
environnement réel — vrai WordPress, vrais conteneurs, vrai drapeau root de
`bin-01` — doit donc être lancée depuis l'onglet **Actions** du dépôt :

1. ouvrir **Actions** → **WordPress — recette et compatibilité** ;
2. **Run workflow** → branche `arena/a792cc4e-secura-academy` → **Run** ;
3. dans les journaux, chercher la ligne
   `scénario 9 : l'exploit obtient un shell root et lit le drapeau`.

Tant que ce run n'a pas eu lieu sur le commit qui contient la réparation, la
ligne « shell root » de `bin-01` reste **non prouvée**. Le run du 12:24 a bien
mesuré `bin-01` (fichier présent, drapeau lisible en root), mais il portait sur
le commit d'**avant** la réparation : il ne pouvait pas prouver qu'un élève
obtient le shell.

### Le banc de mesure ne peut plus échouer en silence

Avant : chaque étape pouvait tuer le job par un `exit 1` anonyme. Après :

- un **registre des échecs** (`/tmp/echecs.txt`) est ouvert au début du run ;
- chaque mesure y note son échec **avec son nom** (« ECHEC : contrôles des
  machines », « ECHEC construction : dojo-01 »…) et le run continue ;
- une étape finale, `Verdict du run de mesure`, écrit le verdict dans le
  sommaire du travail et échoue **en nommant** ce qui a échoué
  (`::error title=Run de mesure en echec::…`) ;
- le code de sortie de la preuve room par room, jusqu'ici calculé puis jeté,
  est désormais pris en compte.

Ainsi le prochain run rouge sera lisible en une ligne, pas après une heure
d'enquête sur des journaux inaccessibles.

Un second workflow existe pour une mesure complète en une commande
(`mesurer-les-machines.yml`), mais GitHub n'autorise son lancement manuel que
lorsqu'il est présent sur la branche par défaut : il faudra le fusionner une
fois pour pouvoir l'utiliser, ou lancer `wordpress.yml`, qui fait le même
travail sur la branche de travail.

## 5. CI : ce qui a changé, et pourquoi

Avant : `ci.yml` et `wordpress.yml` se déclenchaient sur `push` (toutes
branches) et sur `pull_request`. Chaque pousse coûtait donc un run complet.

Après :

```yaml
on:
  push:
    branches: [ main ]   # une pousse sur une branche de travail ne lance rien
  workflow_dispatch:     # mesure manuelle, à la demande
```

- `pull_request` est retiré : la fusion ne déclenchera rien tant que ce n'est
  pas rebranché volontairement.
- La vérification PHP et les tests du dépôt ont été déplacés dans l'action
  partagée `.github/actions/preuves-machines`, pour qu'une seule commande
  mesure vraiment tout (la mesure manuelle hérite donc des contrôles de l'ancien
  CI).
- Au moment de la mise en service, il suffira de remettre
  `pull_request: branches: [ main ]` : un seul run, sur la demande de fusion.

## 7. Journal honnête de la soirée du 5 novembre : 16 runs, et un échec non résolu

Cette section existe parce que la règle est de ne jamais annoncer comme
résolu ce qui ne l'est pas. **`bin-01` n'est PAS validé en conteneur.**

### Ce qui a été réellement réglé (mesuré)

| Défaut | Preuve |
|---|---|
| Le binaire n'avait aucun chemin vers un shell | `carnet_root` ajoutée ; exploit obtient `uid=0(root)` **avec sudo, hors conteneur** |
| `no-new-privileges` neutralisait le setuid | `allow_setuid` dans le manifeste ; prouvé par `setpriv --no-new-privs` |
| L'option était placée **après** l'image → Docker la prenait pour la commande | `verifier-commandes-docker.php` ; c'était **ma** régression, elle cassait Alice et Bob |
| Deux Dockerfiles cassés (commentaire après `\`) | `verifier-dockerfiles.py` ; 10/10 propres |
| Le drapeau fuyait dans un terminal simulé | `cat /root/flag.txt` → `Permission denied` |
| Un `curl` sans corps (`exit 23`) faisait échouer le run | corrigé |
| Le code de sortie de la preuve était calculé puis jeté | pris en compte |
| Le test ne savait pas distinguer « cassé » de « non mesurable » | trois états : réussi / échec / non mesurable |
| `docker cp` échouait sur le `/tmp` tmpfs | passage par l'entrée standard |

### Ce qui n'est pas résolu

Dans le conteneur, en utilisateur `ctf`, **l'exploit n'obtient pas de shell**,
alors que :

- le même exploit, **en root dans le même conteneur**, obtient un shell root ;
- le fichier porte bien `-rwsr-xr-x root root` ;
- `NoNewPrivs` vaut `0` ;
- le montage racine **n'a pas** `nosuid` (hypothèse testée et **écartée**) ;
- le binaire se termine avec le **code 1**, pas un `SIGSEGV`.

Donc : le binaire est correctement détourné (code 1 = `carnet_root` n'a pas
pu ouvrir de shell), mais `execl("/bin/sh")` échoue **après** `setuid(0)`.
C'est le comportement classique d'un noyau qui refuse l'élévation setuid pour
ce processus-là — mais aucune des causes usuelles n'est presente.

### Le vrai problème méthodologique

J'ai consommé **16 runs de vingt minutes** en corrigeant un maillon à la fois,
parce que **mon canal d'observation est défaillant** : les journaux complets
sont sur un stockage inaccessible, les artefacts aussi, et les annotations
GitHub sont plafonnées et tronquées (le dernier run a échoué en n'affichant
que « Process completed with exit code 1 » sur une étape nommée, sans le
détail que mon annotation était censée porter).

Continuer ainsi serait du gâchis. La bonne façon de finir ce point :

1. **reproduire localement l'élévation setuid impossible** — par exemple avec
   `incus`/`LXC` (qui permet de régler `security.nesting`,
   `security.privileged` et de monter un système de fichiers sans `nosuid`),
   ou en écrivant dans `/tmp` un binaire setuid sur un ext4 monté sans
   `nosuid` ;
2. si l'élévation est reproductible en local, corriger en boucle **sans CI** ;
3. ne relancer la mesure GitHub **qu'une fois**, quand la cause est comprise.

C'est ce que ferait un développeur senior : arrêter de payer 20 minutes par
hypothèse.

### Ce qui reste vrai, et qui compte

Le contenu de la room est désormais **honnête** : elle ne promet plus un
drapeau qui traîne dans un fichier, le binaire contient un vrai chemin
d'exploitation, et le test échoue quand le scénario est impossible — au lieu
de passer au vert sur une promesse fausse, comme c'était le cas ce matin.

### 7 bis. Reproduction locale : deux hypotheses testees, deux hypotheses ecartees

Le bac a sable Arena dispose de `sudo` et sait monter : les essais coutent deux
secondes au lieu de vingt minutes. Resultats mesures :

| Hypothese | Test | Resultat |
|---|---|---|
| Le montage racine du conteneur est `nosuid` | lecture de `/proc/mounts` dans le conteneur | **ecartee** : `nosuid` absent |
| Un systeme de fichiers **overlayfs** bloque le setuid (le conteneur tourne sur overlay) | overlay monte localement, binaire setuid root dessus, execute par uid 1000 | **ecartee** : `uid=0(root)` obtenu |
| Un **espace de noms utilisateur** rend le proprietaire root « non mappe » et annule le setuid | `unshare -U -r` : le binaire apparait `nobody nogroup` | **ecartee pour ce cas** : avec root mappe, le setuid fonctionne ; et dans le conteneur le fichier apparait bien `root root` |
| Les **capacites** sont necessaires a l'elevation | `setpriv --bounding-set=-all --inh-caps=-all --ambient-caps=-all` | **ecartee** : `uid=0(root)` obtenu |

Ce qui reste, et qui n'est pas testable d'ici : une **politique du moteur de
conteneur** (profil seccomp, ou runtime rootless) qui intercepte l'elevation.
Cela se lit avec une seule commande :

```bash
docker info --format '{{.SecurityOptions}} | {{.Driver}} | {{.CgroupVersion}}'
```

Plutot que de payer un run de vingt minutes pour cette seule ligne, la sonde
sera ajoutee a la **prochaine** mesure, avec `--security-opt seccomp=unconfined`
en variante de diagnostic : si l'exploit reussit dans cette variante et pas
dans l'autre, le profil seccomp est la cause, en une seule comparaison.

## 9. 6 novembre — bin-01 redessiné sans setuid, et vérifié

### 9.1 La décision
Le binaire setuid root a été abandonné. Quatre runs (18 à 21) avaient
mesuré la même chose : `nosuid` absent de `/`, `NoNewPrivs: 0`, le même
exploit lancé en root donne `uid=0(root)` — l'élévation setuid est
neutralisée par la configuration du moteur, pas par une erreur du lab.
Garder ce montage, c'était promettre un shell root que personne
n'obtiendrait. Le scénario est donc redessiné **sans aucun privilège** :

| Élément | Avant | Après |
|---|---|---|
| Cible | `carnet_root` (ouvre un shell après `setuid(0)`) | `lire_drapeau` (affiche le drapeau, puis `exit(0)`) |
| Privilège | binaire `4755 root:root` | aucun (`755 ctf:ctf`) |
| Drapeau | `/root/flag.txt` en 400 | deux blocs XOR dans le binaire, recombinés par la cible |
| `strings` | donnait le drapeau | ne donne rien (`grep -c SECURA` = 0) |
| Portabilité | dépendait du moteur | n'importe quel conteneur, n'importe quel noyau |

### 9.2 Ce qui a été mesuré, pas supposé
- Local, uid 1000, aucun setuid : `FLAG=SECURA{buffer_overflow}`, code 0.
- Le même exploit lancé par l'entrée standard (`python3 -`), comme dans le
  banc de test : même résultat.
- `nm vulnerable` → `0000000000401176 T lire_drapeau` (l'adresse a changé
  avec l'ajout de `exit(0)`, l'outil la lit tout seul : rien à figer).
- Run GitHub **42132855061** : **71 contrôles réussis, 0 échec, 0 non
  mesurable**, et l'annotation du scénario 9 nomme le drapeau obtenu.

### 9.3 Le défaut trouvé en chemin
En réécrivant le Dockerfile, la première version supprimait
`COPY flag/flag.txt /root/flag.txt` en croyant que le fichier ne servait
plus. C'était faux : `Secura_Lab::read_file()` le lit **en root dans le
conteneur** pour valider la réponse de l'apprenant. Sans lui, la room
devenait invalidable. Le fichier est donc conservé comme **corrigé du
serveur** (400 root:root), et le banc de test vérifie les deux côtés :
illisible en uid 1000, lisible en root en tant que `uid=0`. C'est
exactement le genre d'erreur qu'un test qui exécute le vrai chemin
attrape, et qu'une relecture rapide laisse passer.

### 9.4 Effet sur les autres workflows
Comme le déclencheur `push` de `labs.yml` avait été élargi à la branche de
